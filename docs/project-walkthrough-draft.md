# AIFPatent 项目迭代原因档案（初稿）

> 版本基线：`feature/agent-upgrade`，HEAD `722a810`，2026-07-29
> 统计口径：读取 `git log --all --reverse` 得到的全部 160 个唯一提交。
> 本文只回答“项目为什么这样一步步迭代”，不承担当前架构说明；当前代码的完整讲解见 `project-code-explained-draft.md`。

## 1. 先看整条演进主线

这个项目并不是一次性设计完成的。它沿着一条很清楚的风险收敛路线演进：

1. **先让核心业务脱离外部 Agent 运行时。** 最初的目标是把 IDEA 评估从 OpenCode 依赖中抽离，改造成仓库内可控制、可测试的 LangGraph 工作流。
2. **再解决“模型结论不可复核”的问题。** 项目引入不可变专利语料、分块、上下文清单、Evidence/Citation 和哈希校验，把“模型说了什么”变成“模型基于哪些冻结证据说了什么”。
3. **再把一次性报告扩展成可追问产品。** 追问不能沿用聊天记录当证据，所以另建冻结范围、每轮重新检索、回答后校验的工作流。
4. **再增加第二条产品线——专利态势分析。** 它从最小的检索、精读、聚类，逐步演进为完整候选集、公司唯一归属、公司内技术分类和跨公司趋势。
5. **最后处理工业化问题。** 包括 PostgreSQL 统一持久化、断点恢复、原子写入、幂等、完整集合审计、受限修复、批处理，以及把大规模逐专利精读从趋势主链路中拆走。

从结果看，项目最重要的架构转折有三个：

- `20587d9`：从外部运行时转向仓库内 LangGraph/LangChain。
- `4267c44`：从 SQLite/Redis 过渡态统一到 PostgreSQL 生产运行时。
- `104a921`：态势分析从“全部专利逐件大模型精读”转向“全量轻量指纹做趋势、代表专利按需深读”。

## 2. 各阶段为什么发生

### 阶段 A：把 IDEA 评估变成独立、可控的工作流（1–6）

触发原因是原系统依赖 OpenCode 运行时，业务流程、并发、模型输出和证据校验都不完全由项目自己控制。这个阶段先建立独立仓库，再用 LangGraph 固化流程，并立刻修补创造性证据绑定和并发问题。第 6 次提交已经暴露出下一阶段的核心矛盾：外部专利检索不稳定，而且模型上下文没有统一、可审计的边界。

### 阶段 B：建立可审计 RAG 基础设施（7–34）

仅把流程搬进 LangGraph 还不够。专利全文如果仍是临时文本，报告无法重放；上下文如果只是临时拼接，Citation 也无法核验。因此这一阶段先定义上下文边界和基础设施接口，再依次补对象存储、PostgreSQL、不可变版本、分块、上下文组装、容器化和历史语料回填，最后形成限定版本范围的 PostgreSQL 关键词检索。

期间连续三个 MinIO 构建修复说明，基础设施不仅要“逻辑上正确”，还必须能在受限网络和最小镜像中真正启动。

### 阶段 C：让首次报告真正由证据驱动（35–46）

语料库已经存在，但业务报告仍需解决四个问题：检索范围是否冻结、摘要/独立权利要求是否一定进入上下文、模型引用是否真实、未来如何兼容向量检索。于是项目先做关键词 RAG MVP，再强制核心证据、持久化上下文、验证 Citation，最后引入 Embedding、pgvector 和 RRF 融合内核。

### 阶段 D：把静态报告扩展成受约束的追问（47–62）

用户拿到报告后自然会继续问“哪里重合”“如何绕开”。普通聊天会产生证据漂移：历史回答可能被下一轮当成事实，模型也可能引用报告摘要而不是专利原文。因此这一阶段单独建立 Thread/Turn、冻结语料版本、固定七步工作流、每轮重新检索和 Citation 验证，并把首次报告与追问共用同一混合检索器。

### 阶段 E：形成专利态势分析 MVP（63–84）

单个 IDEA 的新颖性分析不能回答“某技术最近有哪些布局”“竞品集中在哪些方向”。因此项目增加第二条独立业务线。MVP 从独立持久化、范围校验、逐专利分析、聚类、API/UI 开始，随后根据输入自动推导技术/竞品/组合模式。

真实检索很快暴露出覆盖不足和 Provider 不稳定问题，所以后半段重点从“能返回结果”转为“所有计划 Query 都执行、每个 Provider 状态都可诊断、SerpAPI 成为稳定入口”。

### 阶段 F：修复检索证据与筛选质量（85–100）

SerpAPI 在态势分析中验证后被引入 IDEA。随后又发现详情抓取可能缺独立权利要求、态势结果的公司/同族代表性不足、竞品别名会导致零召回，于是逐项修复。

`4267c44` 是生产化拐点：SQLite、Redis 和 PostgreSQL 并存会造成事实源分裂，因此生产运行时统一到 PostgreSQL；下一次提交马上拓宽 IDEA 查询，说明数据库统一之后，团队又回到业务召回质量。

### 阶段 G：把态势分析从“聚类样本”升级成“全量公司趋势”（101–130）

早期态势分析只对有限样本精读再聚类，不能保证所有合格专利都进入公司统计。新目标要求定义完整集合 `U`，给 `U` 中每件专利唯一分配公司，抓取完整集合，按公司分类并生成跨公司趋势。

这不是简单增加几个 Prompt，而是增加候选集、公司注册表、唯一归属、抓取状态、公司结果清单、跨公司结果、覆盖审计、公司级任务键和 LangGraph fan-out。旧聚类主链路最终被淘汰，报告升级到 v2。

### 阶段 H：让全量公司趋势可以审计、修复和恢复（131–140）

全量流程中，某一家公司分类失败或某条趋势证据不完整，不应该重跑全部搜索，也不应该偷偷忽略。因此项目引入最多一轮、只处理审计目标的受限修复；修复前后结果采用追加式快照，主图按 PASS/REPAIR/LIMITED 路由，并补上进程恢复和启动迁移。

### 阶段 I：用批处理与轻量指纹降低全量分析成本（141–160）

全量逐专利调用大模型的成本和时延会随 `U` 线性放大，还会让趋势报告被少数详情抓取失败卡住。因此项目先做批量抓取/分析，再冻结“轻量方向指纹”架构：每件专利用题名、摘要/片段、权利要求开头和少量说明书形成确定性指纹；公司分类和趋势基于全量指纹；只有确定性选出的代表专利才进入可选深度精读。

最后三次修复集中在分类器 ID：模型不应决定数据库主键，分类 ID 必须由程序规范化并在批次合并后保持稳定。这是典型的“把身份控制权从模型收回程序”的工业化收尾。

## 4. 几条最值得串讲的因果链

### 4.1 为什么项目反复强调“冻结”

`Patent Document → Version → Chunk → Context Manifest → Citation → Report`

每个箭头都在解决同一个问题：如果后续重新抓到的正文、重新分块的结果或模型上下文发生变化，旧报告仍必须能够解释。冻结的不是“模型答案”，而是模型当时允许看到的事实范围。

### 4.2 为什么模型越来越多，程序校验也越来越多

模型被用于术语扩展、技术理解、分类和叙述；程序掌握 ID、集合、日期、唯一性、状态转换、证据归属和最终完成门槛。后期的 Category ID 修复最能说明这一点：模型可以给类别命名，但不能决定持久化身份。

### 4.3 为什么态势分析从全量精读改成轻量指纹

全量精读保证信息丰富，却把成本、时延和失败面都乘以候选数。轻量指纹保留了全量覆盖，分类与趋势仍处理 `U`；深度分析只处理确定性代表集 `M`。这是从“以模型调用为中心”转向“以完整数据集为中心”。

### 4.4 为什么生产最终统一 PostgreSQL

早期 Redis 负责队列/限流、SQLite 负责业务事实、PostgreSQL 负责 RAG，会出现恢复点和真相来源分裂。统一 PostgreSQL 后，业务结果、语料元数据、追问、Landscape、缓存元数据和步骤状态都能在同一事务系统中检查；对象存储只负责大正文。

## 6. 建议的迭代史串讲顺序

1. 先用三句话说明初始矛盾：外部运行时依赖、结论不可审计、检索不稳定。
2. 讲 `20587d9`、`4267c44`、`104a921` 三个拐点。
