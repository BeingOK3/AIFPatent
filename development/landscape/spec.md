# 专利态势重构产品需求规格

状态：`approved-product-baseline`

版本：`1.1`

建立日期：`2026-08-03`

## 0. 文档定位

本文定义专利态势重构的产品目标、用户输入、检索范围确认、专利分类、
趋势输出、证据和验收边界，是新版本唯一产品事实源。

本文暂不规定 LangGraph 节点、数据库表、并发算法、模型 Prompt、聚类算法或
代码模块。上述内容在本需求确认后另行设计，不得反向改变已确认的产品语义。

本版本是干净重构，不兼容旧 Landscape 的配置、预算字段、API、Run 续跑、
报告 Schema 或精读入口；不建立旧配置转换层。新链完成对应能力验收后，
直接删除旧代码、旧配置和旧产品入口。

当前分类基线为 [`classify.md`](classify.md)。实现必须为其建立稳定版本；分类
标准后续更新不得改变旧 Run 使用的历史版本和既有结果。

规范用词：

- “必须”：产品和验收不能省略；
- “应当”：默认行为，偏离时必须说明原因；
- “可以”：不影响核心语义的可选能力。

## 1. 产品目标

系统面向用户指定的公开时间窗，通过可审查的公司名称和技术检索词构建检索
范围，对范围内的去重专利进行有证据的技术分类，并输出按技术类别、申请机构
和时间组织的专利态势。

核心目标：

1. 支持仅公司、仅技术方向、公司与技术方向三种输入模式；
2. 公司名称扩展和技术词扩展必须先由用户审查，再进入正式检索；
3. 记住用户确认过的公司名称范围，并在后续任务中持续复用和更新；
4. 中文和英文检索词共同参与检索，降低单语检索遗漏；
5. 优先使用用户提供的分类标准对全部可分析专利进行统一分类；
6. 只有摘要证据足以识别技术方向、但无法匹配既有分类时才进入 `Others`，再
   识别其中的新技术方向；
7. 趋势、统计和代表专利必须能回溯到本次冻结范围和实际专利证据；
8. 新版本默认处理 500 件去重分析专利，单次执行必须稳定支持 1000 件；超过
   1000 件时使用可恢复分片继续处理，单件失败不得轻易导致整次分析失败。

系统输出的是“本次已确认检索范围和数据来源内的专利态势”，不宣称全球穷尽，
也不构成法律意见、公司控制关系认定或专利有效性意见。

## 2. 输入模式

所有模式都必须包含公开时间窗。公司和技术方向的组合决定分析模式。

| 模式 | 必填输入 | 检索问题 |
|---|---|---|
| `COMPANY_ONLY` | 1～N 个公司、时间窗 | 这些公司在时间窗内布局了哪些技术 |
| `TECHNOLOGY_ONLY` | 技术方向、时间窗 | 该技术方向由哪些公司、学校等机构参与 |
| `COMPANY_AND_TECHNOLOGY` | 1～N 个公司、技术方向、时间窗 | 指定公司在该技术方向内如何布局 |

系统必须根据实际输入确定模式。不能让模型自行增加公司、改变时间窗或把组合
模式降级成更宽的仅公司/仅技术模式。

## 3. 检索范围确认

### 3.1 两阶段交互

创建分析分为两个明确阶段：

1. **范围准备**：生成公司名称候选和技术检索词候选；
2. **范围确认**：用户增、改、删并确认后，才允许正式检索。

未经用户确认的模型建议不得直接进入正式检索。确认后必须保存本次 Run 的
不可变范围快照；以后知识库发生变化时，不得改写旧 Run 的范围和报告。

### 3.2 公司范围对象

每个用户输入公司对应一个可持续更新的“公司检索范围档案”。档案至少表达：

- 用户识别该公司或集团时使用的主名称；
- 中文和英文法定主体名称；
- 翻译名称、常用简称和历史名称；
- 经用户确认纳入范围的子公司或集团成员；
- 每个名称的关系类型、来源和当前状态；
- 历次用户确认形成的版本。

“同一主体的别名”和“集团成员/子公司”必须作为不同关系保存。两者都可以在
用户确认后参加检索，但报告不得把集团范围描述成单一法律主体。

### 3.3 公司名称记忆闭环

首次输入某公司时：

1. 系统保留用户原始输入；
2. 模型生成中英文名称、简称、历史名称和可能的集团成员候选；
3. 系统逐项展示候选及其关系类型和来源；
4. 用户可以新增、修改、启用、排除或恢复候选；
5. 用户确认后，冻结本次检索范围并写入公司范围档案。

再次输入该公司，或输入档案中任一可识别名称时：

1. 系统找到对应档案并加载最近一次用户确认的有效名称；
2. 模型基于历史档案提出增量建议，而不是从零生成；
3. 已被用户排除的名称默认不得被当作新候选反复推荐；
4. 用户再次审查并确认；
5. 确认结果生成档案新版本，同时冻结为本次 Run 的范围快照。

公司名称记忆的核心公式为：

```text
历史用户确认集合
+ 本次模型增量建议
+ 本次用户人工修订
= 本次冻结公司检索范围
```

模型生成的名称永远只是候选。只有用户确认的名称可以进入正式公司过滤和公司
归属统计。

### 3.4 技术方向扩展

系统必须根据用户输入方向的实际语义范围生成中英文检索词候选，而不能仅按
输入字符串长度判断方向宽窄。

- 输入较宽时，补充必要的标准名称、常用别称和英文表达，但不得无边界扩大；
- 输入较窄时，可以补充同义词、缩写、上下位术语、关键组件、常用表达和中英
  文对应词，以提高召回；
- 中文输入必须生成英文候选，英文输入必须生成中文候选；
- 每个候选应显示语言、来源及其与原始方向的关系；
- 用户可以新增、修改、删除或恢复候选；
- 只有用户确认后的词可以进入正式检索；
- 本次确认结果必须进入不可变 Run 快照。

模型不得把相邻但不同的技术方向悄悄纳入范围。无法确定是否越界的候选必须保留
为待用户确认，而不是默认启用。

### 3.5 三种模式的检索逻辑

逻辑上的查询边界为：

```text
COMPANY_ONLY:
  company_name_1 OR company_alias_1 OR confirmed_member_1 ...

TECHNOLOGY_ONLY:
  chinese_term_1 OR english_term_1 OR synonym_1 ...

COMPANY_AND_TECHNOLOGY:
  (confirmed company names)
  AND
  (confirmed technology terms)
```

当组合模式包含多个公司时，系统应保证每个公司都有独立检索机会，再合并、过滤
和去重结果；不得因单一公司的结果占满 Provider 排名而静默漏掉其他公司。

## 4. 检索结果集合

正式分析范围必须经过：

1. Provider 检索；
2. 公开号和公开日期校验；
3. 按本次确认范围执行公司/技术条件过滤；
4. 跨查询结果去重；
5. 形成冻结分析集合，并在需要时形成确定性的执行分片。

系统必须记录 Provider 报告的结果规模、实际读取范围、过滤原因、去重结果和
停止原因。达到 Provider 上限或产品上限时必须明确标记受限范围，不能静默截断
后声称覆盖了全部结果。

规模规则为：

- 默认正式分析规模为 500 件；
- 501～1000 件可以作为一个单次执行完成；
- 超过 1000 件时，必须向用户显示预计规模、成本和时间并获得确认，再拆成每片
  不超过 1000 件的可恢复任务；
- 多个执行分片仍属于同一个逻辑 Run，最终统计必须基于完整冻结集合合并；
- 分片不得改变专利成员、分类结果和统计口径。

产品不设置一个伪装成技术能力的“无限”开关。实际可处理总量仍受检索 Provider
分页、用户确认范围、模型额度和运行预算约束；任何停止原因都必须明确显示。

## 5. 专利证据读取

### 5.1 摘要证据

系统读取每件专利的标题和摘要，并以其作为本版本技术分类的全部文本证据。
分类结果必须引用实际使用的专利内容，不能只根据公司、日期、国家或检索排名
分类。

### 5.2 证据充分性判断

系统必须判断标题和摘要是否足以支持可靠分类。以下情况至少应视为可能不足：

- 摘要只描述目标或效果，没有说明技术机制；
- 摘要过短、缺失或只有通用背景；
- 两个或多个既有分类均可能成立，无法确定主分类；
- 分类理由无法绑定到摘要中的实际内容。

### 5.3 摘要不足与 `UNRESOLVED`

本版本暂不补读独立权利要求或说明书全文。标题和摘要不足以支持可靠判断时：

- 不得编造技术机制或强行选择分类；
- 分类状态必须为 `UNRESOLVED`；
- 必须记录摘要缺失、内容不足、候选冲突或技术失败等具体原因；
- `UNRESOLVED` 不得伪装成 `Others`，也不得计入某个正式主分类；
- 单件 `UNRESOLVED` 不得导致整个 Run 失败；
- 报告必须单独显示其数量、占比和专利清单。

后续版本可以增加权利要求或全文精读，但不属于当前态势分析需求。

## 6. 分类标准

### 6.1 分类基线

系统必须优先使用本次 Run 冻结的 `classify.md` 版本。分类表表达可变深度路径：

```text
一级分类 → 二级分类 → 可选三级分类
```

分类时必须匹配到分类表中最深的已定义层级：

- 表中定义了三级分类时，可以分类到三级；
- 表中三级为空时，分类到二级即为完整有效结果；
- 不得因为三级为空而由模型自行创造一个正式三级分类；
- 分类标准的后续修改不得改变旧 Run 的既有分类结果。

### 6.2 主分类与辅助标签

每件成功分类的专利必须具有且仅具有一个主分类路径，用于数量、占比和趋势
统计，确保各主分类之和能够与冻结分析集合对账。

专利可以具有零到多个辅助技术标签，以表达跨领域特征。辅助标签不能重复计入
主分类专利数量，也不能改变主分类成员关系。

每个分类结果至少包含：

- 专利身份；
- 分类状态：`CLASSIFIED | OTHERS | UNRESOLVED`；
- 主分类路径；
- 辅助标签；
- 分类置信度；
- 简短分类理由；
- 支持该分类的证据引用；
- 摘要证据是否充分及不足原因；
- 使用的分类标准版本。

`CLASSIFIED` 和 `OTHERS` 必须具有主分类；`UNRESOLVED` 的主分类必须为空。
三个状态互斥且必须完整覆盖冻结分析集合：

```text
冻结分析集合 = CLASSIFIED + OTHERS + UNRESOLVED
```

公司名称、申请机构类型、公开日期和检索词命中不得成为技术分类本身的特征。

### 6.3 `Others`

只有在标题和摘要已经足以识别专利技术方向，但该方向无法匹配分类标准中的任何
有效路径时，才允许将其分类状态和主分类设为 `Others`。不得因为模型超时、
摘要缺失、证据抓取失败或证据不足，就把专利方便地放入 `Others`；这些对象
必须进入 `UNRESOLVED`。

系统必须对本次 Run 中全部 `Others` 再进行技术方向区分，依据技术问题、解决
机制和技术对象形成一个或多个“新方向候选”。

`Others` 新方向：

- 只在本次 Run 中生效；
- 必须保留成员专利和证据；
- 必须有可读名称和方向说明；
- 不得自动写回或修改正式分类标准；
- 后续可以由用户另行审查，决定是否纳入未来分类版本。

`Others` 为空时不得为了输出完整形式而虚构新方向。

## 7. 申请机构归一

技术方向模式下，系统需要从检索结果识别公司、学校及其他申请机构，并保留
Provider 返回的原始申请人名称。规范化只用于合并可以确认的同一机构，不得
仅凭名称相似度推断集团控制关系。

公司输入模式下，公司归属只能使用本次经用户确认的公司范围。无法确认归属的
专利必须进入明确的未确认集合，不能被模型强行分配给某家公司。

一件专利存在多个申请机构时必须保留全部已知机构，不得静默丢弃共同申请人。
具体统计展示可以选择主申请机构视图或共同申请视图，但必须公开口径并保持可
复算。

## 8. 三种模式的分析视图

### 8.1 仅技术方向

系统围绕用户确认的技术范围组织结果：

```text
技术分类
→ 公司/学校等申请机构
→ 时间分布与变化
→ 代表专利
```

申请机构来自实际检索结果。系统应展示主要参与机构、各机构在不同技术分类中的
布局、共同方向、差异方向和有足够时间证据支持的变化。

### 8.2 仅公司

系统分析所选公司在时间窗内的完整专利技术组合：

```text
公司
→ 技术分类
→ 时间分布与变化
→ 公司间比较
→ 代表专利
```

该模式不受某个用户输入技术方向限制，回答“这些公司正在布局哪些技术”。当只
输入一家公司时，不强制生成跨公司比较。

### 8.3 公司与技术方向

系统只分析确认公司范围和确认技术范围的交集：

```text
技术分类
→ 公司
→ 各公司的路线、共同点和差异
→ 时间分布与变化
→ 代表专利
```

该模式回答“这些公司在指定技术领域内分别如何布局”，不得混入公司在其他领域
的专利。

## 9. 趋势要求

趋势必须基于完整主分类成员、申请机构归属和公开时间数据计算，不能只基于少量
代表专利或模型印象。

系统至少应输出：

- 各主分类的专利数量和占比；
- 各公司/学校在主分类中的分布；
- 不同时间段的数量和组成变化；
- 有证据支持的新增、持续活跃、增强、减弱或方向转移；
- 数据不足、时间桶不足和受限检索造成的限制；
- `Others` 及其本次新方向候选。

模型可以解释程序已经确认的统计和方向，但不能自行计算数量、修改分类成员或在
时间证据不足时声称增长、下降、加速或转移。

当只有一个有效时间段或样本过少时，系统只能输出“当前布局”或“观察”，不能
包装成趋势。

## 10. 代表专利与链接

每个重要技术方向或趋势应同步展示少量代表专利。代表性应综合考虑：

- 与该分类或趋势的相关性；
- 分类置信度和证据完整性；
- 时间代表性；
- 公司/学校覆盖；
- 避免同一专利族重复占位。

代表专利必须来自该方向的真实成员，不能由模型新增公开号。每个条目至少展示
专利名称、公开号、申请机构、公开日期、分类路径和入选原因。

专利名称必须作为超链接，在浏览器新页面打开对应的公开专利详情页。链接必须由
程序使用真实公开号和允许的专利站点生成；模型不得生成或改写 URL。链接不可用
时仍保留专利名称和公开号，并明确标记不可用。

## 11. 用户可见的范围与审计

报告必须让用户看到：

- 原始公司输入；
- 实际确认的每家公司名称范围及版本；
- 原始技术方向；
- 实际确认的中英文技术检索词；
- 公开时间窗；
- Provider、分页/读取范围和停止原因；
- 原始命中、过滤、去重、冻结分析集合和失败数量；
- 分类标准版本；
- 摘要分类和 `UNRESOLVED` 数量、占比及原因；
- `Others` 数量及其新方向；
- 趋势限制和代表专利依据。

任何限制都不得只存在于后台日志中。

## 12. 稳定性与恢复要求

500 件默认规模和 1000 件单次最大规模必须满足：

- 单件摘要、分类或链接失败不导致全局失败；
- 已成功完成的单件结果能够保存，重试只处理未完成或失败对象；
- 模型限流、超时或暂时不可用时可以重试、降级或受限完成；
- 取消和服务恢复后，不重复消耗已经确认成功的工作；
- 任一高阶叙述失败时，仍可基于已完成分类和程序统计生成基础报告；
- 不存在把全部 500 或 1000 件摘要放入一次模型请求的路径；
- 并发只能影响完成速度，不能改变检索集合、分类成员和统计结果。

超过 1000 件的逻辑 Run 还必须满足：

- 每个分片可独立 checkpoint、重试和恢复；
- 已成功分片不得因其他分片失败而重做；
- 合并前后不存在重复专利或静默遗漏；
- 分片执行顺序不得改变最终分类和统计结果。

具体并发数、动态限流策略和延迟目标在技术设计与真实 Provider 基准测试后冻结。

## 13. 隐私与安全

- 模型和 Provider API Key 不得进入数据库、报告、前端持久存储、日志或 Git；
- 用户确认的公司范围和技术词属于业务数据，必须按项目数据权限处理；
- 外部专利链接只能使用配置允许的域名；
- 模型输出中的公司、专利号、分类路径和证据引用都必须由程序校验；
- 历史 Run 必须保留当时的范围和分类版本，不被后续知识更新改写。

## 14. 非目标

本版本不要求：

- 自动认定公司之间的法律控制或股权关系；
- 未经用户确认自动扩大公司或技术检索范围；
- 自动把 `Others` 新方向写回正式分类标准；
- 读取独立权利要求或说明书全文；
- 用代表专利代替完整分类统计；
- 对样本不足的数据生成强趋势；
- 承诺不受 Provider、模型额度、运行预算和用户确认约束的无限处理；
- 在本需求阶段冻结 LangGraph 节点和具体 Agent 实现。

## 15. 产品验收场景

### 15.1 公司名称记忆

1. 首次输入“华为”，模型提供中英文主体、别名和集团成员候选；
2. 用户删除错误名称、增加一个公司名称并确认；
3. 新 Run 只使用用户确认集合；
4. 再次输入“华为”或一个已确认成员名称时，自动加载历史集合；
5. 模型只提供增量候选；
6. 历史排除项不被默认重复推荐；
7. 新确认生成新版本，但旧 Run 仍显示旧版本快照。

### 15.2 双语技术方向

1. 输入中文窄方向，系统生成相关但不越界的中英文候选；
2. 用户可以增、改、删；
3. 正式查询只使用确认词；
4. 报告显示实际查询范围。

### 15.3 分类与 `Others`

1. 能匹配分类表二级或三级的专利进入最深已定义路径；
2. 三级为空时不生成虚假三级类别；
3. 一件专利只有一个统计主分类，可以有辅助标签；
4. 摘要足以识别技术方向、但无法匹配现有路径的专利进入 `Others`；
5. Agent 对全部 `Others` 形成有成员和证据的新方向候选；
6. 新方向不自动修改正式分类标准。

### 15.4 证据不足

1. 摘要足够时直接完成分类；
2. 摘要不足时不读取独立权利要求或全文；
3. 该专利进入 `UNRESOLVED` 并记录具体原因；
4. 只有摘要足以识别技术方向、但确实无法匹配现有分类路径时才进入 `Others`；
5. `UNRESOLVED` 和技术失败不得伪装成 `Others`；
6. 单件失败不影响其他专利和基础报告。

### 15.5 三种报告模式

1. 仅技术方向按技术分类展示公司、学校等实际申请机构；
2. 仅公司按公司展示其完整技术组合；
3. 公司与技术方向只展示两者交集，并按技术分类比较公司；
4. 单公司场景不生成虚假跨公司差异；
5. 代表专利名称可在新页面打开真实详情页。

### 15.6 500、1000 件与分片稳定性

1. 500 件默认规模能够稳定完成逐件摘要判断和分类；
2. 1000 件单次最大规模能够完成同样的完整流程；
3. 超过 1000 件时按确定性规则分片，并合并为同一个逻辑报告；
4. 单件或单片失败可独立重试或降级；
5. 中断恢复不重做全部成功项；
6. 基础统计与主分类、`Others`、`UNRESOLVED` 成员严格对账；
7. 高阶叙述失败不导致整个 Run 丢失。

## 16. 需求评审结论

本版本冻结以下产品方向：

1. 三种输入模式；
2. 公司名称范围具有“历史确认、模型增量建议、用户再次确认、版本更新”的记忆
   闭环；
3. 公司别名与集团成员关系分开保存；
4. 技术方向使用经用户确认的中英文扩展词；
5. 组合模式采用公司名称组与技术词组的交集；
6. 当前版本只使用标题和摘要，不读取独立权利要求或说明书全文；
7. 每件专利采用一个主分类和多个可选辅助标签；
8. 摘要不足时进入 `UNRESOLVED`；摘要足以识别方向但无法匹配版本化分类标准
   时才进入 `Others`；
9. `Others` 由 Agent 形成 Run 内新方向，但不自动修改正式标准；
10. 三种模式使用不同主视角输出趋势和代表专利；
11. 代表专利链接由程序生成并在新页面打开；
12. 默认正式分析规模为 500 件，单次最大规模为 1000 件，超过 1000 件使用
    可恢复分片，稳定和可恢复优先。
13. 新版不兼容旧 Landscape 配置、API、Run 和报告，不保留新旧双轨运行。

本文已经用户确认。后续技术架构和实施必须以本版本为边界；产品需求发生变化时
先升级本规格版本，再同步调整开发规格。
