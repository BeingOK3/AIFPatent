# AI4Patent IDEA 当前架构说明与下一阶段开发意见

> 第一部分用通俗语言解释当前实现；第二部分从架构师角度给出下一阶段完整路线图。

先给结论：现在的 IDEA 模块已经不是“给大模型一段提示词，让它自己搜索并写报告”的简单脚本，而是一条由后端程序牢牢控制的专利分析流水线。

它的定位比较准确：适合做内部专利检索和申请前预评估，强调“过程可追踪、证据能回查、模型不能随便编”。但它还不能替代专业检索数据库、专利代理师或正式法律意见。

## 一、大白话理解整体架构

可以把它想象成一家专利评估工厂：

```text
用户提交技术方案
        ↓
工厂调度员：固定 Workflow，决定下一步干什么
        ↓
AI 专员：负责理解文字、分析语义、写判断
        ↓
普通程序：负责检索、去重、日期、证据、状态、校验
        ↓
质检员：检查证据和结论是否对应
        ↓
SQLite + 本地文件：保存全过程和最终报告
```

最关键的一点是：

> AI 是流水线里的工人，不是工厂厂长。

模型不能自己决定跳到哪一步，也不能自己声称“我搜索到了某专利”。整个控制顺序由 [workflow.py](../backend/idea/workflow.py#L12) 和 [execution.py](../backend/idea/execution.py#L38) 决定。

## 二、用户提交以后，系统具体做了什么

### 1. 创建 Case 和 Run

Case 是“同一个技术方案的历史文件夹”。

Run 是这个文件夹下的“一次具体评估”。

例如：

```text
Case：机械臂视觉抓取方案
├── Run 1：第一次描述，评估日 2025-01-01
├── Run 2：增加深度相机特征后的描述
└── Run 3：修改检索范围后的重新评估
```

每个 Run 都是不可覆盖的快照。输入文字、评估日、检索预算、模型名称和报告分别保存。

API Key 不保存，只在这次 Run 的后端内存中存在。任务结束、失败、取消或者服务重启后就丢失。相关逻辑在 [api.py](../backend/idea/api.py#L102)。

### 2. 固定执行 11 个步骤

当前 Workflow 是：

1. `PREPARE_INPUT`：保存不可变输入快照。
2. `PARSE_IDEA`：AI 把技术方案拆成 F1、F2、F3 等必要技术特征。
3. `VALIDATE_IDEA_MODEL`：程序检查特征编号、原文位置和必要特征是否合理。
4. `PLAN_QUERIES`：AI 生成中英文检索式、同义词、上位词和分类号候选。
5. `RETRIEVE_CANDIDATES`：并行调用 EXA 和 Google Patents。
6. `NORMALIZE_AND_FETCH`：统一公开号、合并重复结果、筛选并抓取全文。
7. `ANALYZE_DOCUMENTS`：AI 逐篇分析专利，判断每个 F 特征是否被披露。
8. `DETERMINE_NOVELTY`：程序根据单篇文献矩阵判断新颖性。
9. `ANALYZE_INVENTIVENESS`：AI 按多个 D1 路线进行创造性三步法分析。
10. `ASSESS_VALUE`：AI 进行可取证性、规避难度和技术市场价值评分。
11. `AUDIT_AND_REPORT`：程序审计、AI语义审计，最后生成报告。

每一步都有：

- 当前状态；
- 第几次尝试；
- 输入和输出哈希；
- 错误类型；
- 开始和结束时间；
- 可恢复检查点。

某一步失败会在配置允许的次数内重试。全部成功以后还要通过最终完成门禁，才能标记为 `COMPLETED`。

## 三、检索部分是怎么工作的

检索不是让大模型凭记忆回答，而是调用两个真实来源：

- 本地编写的 Google Patents 抓取 Provider；
- EXA MCP Provider。

这里的“本地 Google Patents”不是离线数据库，只是抓取程序写在本地，仍然需要访问 `patents.google.com`。

实际流程是：

```text
AI 生成检索式
    ↓
每条检索式同时发给两个 Provider
    ↓
保存每一路原始结果
    ↓
按公开号、申请号、同族 ID、URL 去重
    ↓
按标题和摘要进行初步相关度评分
    ↓
排除评估日之后的文献
    ↓
选出需要全文深读的专利
    ↓
Google Patents 抓取失败时，尝试 EXA 备用抓取
```

检索编排在 [retrieval.py](../backend/idea/retrieval.py#L60)，Google Patents 抓取在 [google_patents.py](../backend/idea/providers/google_patents.py#L1)，EXA MCP 在 [exa.py](../backend/idea/providers/exa.py#L1)。

系统不会为了凑够十篇而塞入明显不相关的文献。如果只有 1～9 篇可用全文，可以继续完成，但新颖性通常会降级为“不确定”；一篇全文都没有则直接失败。

## 四、专利文献是怎么分析的

每篇专利会单独交给一个 Document Agent。

它不会获得所有专利全文，而只获得：

- 当前专利的基本信息；
- 用户方案的 F1～Fn；
- 摘要；
- 权利要求；
- 与技术特征较相关的说明书片段。

后端先把这些片段做成证据包，并给出临时短编号：

```text
E1：权利要求1……
E2：摘要……
E3：说明书第0023段……
```

Agent 对每个特征只能输出：

- 已披露；
- 部分披露；
- 未披露；
- 不确定。

如果说“已披露”或“部分披露”，必须引用 E1、E2 之类的真实证据。后端再把短编号转换成带哈希的长期 evidence ID。

如果模型编造 `E99`，或者引用了另一篇专利的证据，程序会拒绝结果。实现位于 [document_analysis.py](../backend/idea/document_analysis.py#L87)。

## 五、新颖性为什么相对可靠一些

新颖性最终不是由报告 Agent 随口判断的，而是程序根据逐篇矩阵计算。

例如：

| 文献 | F1 | F2 | F3 | 是否单篇破坏新颖性 |
|---|---|---|---|---|
| 专利 A | 已披露 | 已披露 | 未披露 | 否 |
| 专利 B | 已披露 | 未披露 | 已披露 | 否 |
| 专利 C | 已披露 | 已披露 | 已披露 | 是 |

即使 A+B 拼起来覆盖所有特征，也不能因此判定不具备新颖性。只有专利 C 这种单篇覆盖全部必要特征的文献，才能破坏新颖性。

这部分由 [novelty.py](../backend/idea/novelty.py#L28) 确定性执行，是当前系统设计得比较扎实的部分。

## 六、创造性和价值是怎么判断的

### 创造性

系统会选出最多三篇最接近的文献作为不同的 D1 路线。

对每条路线：

1. 找出 D1 没有披露的区别特征；
2. 从其他已深读文献中寻找 D2 证据；
3. 判断 D2 是否披露区别特征；
4. 判断本领域技术人员是否有组合动机。

每条路线由一个独立 Agent 调用并发分析，但它不能自己继续搜索，只能使用后端提供的 D2 和证据。相关实现是 [inventiveness.py](../backend/idea/inventiveness.py#L43)。

### 价值

价值 Agent 不再读取专利全文，只读取已经冻结的：

- IDEA 特征；
- 技术效果；
- 新颖性结论；
- 创造性路线。

然后对三个维度给出 1～5 分：

- 可取证性；
- 规避难度；
- 技术/市场价值。

它还会给出申请建议和替代方案，但不能修改前面的新颖性、创造性结论。实现位于 [value_analysis.py](../backend/idea/value_analysis.py#L27)。

## 七、Agent 到底是怎么设计的

现在一共有七种 Agent 角色：

| Agent | 负责什么 | 明确不能做什么 |
|---|---|---|
| Idea Parser | 拆技术特征 | 不搜索、不判断新颖性 |
| Query Planner | 生成检索式 | 不声称已执行搜索 |
| Document Analyzer | 分析单篇专利 | 不跨文献拼接 |
| Inventive Step Analyzer | 分析单条 D1/D2 路线 | 不自主搜索 |
| Value Analyzer | 价值预评估 | 不修改法律结论 |
| Evidence Auditor | 检查证据是否支持表述 | 不直接改写结论 |
| Report Composer | 把冻结结果写成人话 | 不创造新事实 |

这里要注意：“七个 Agent”不等于七个真正独立的智能体。

它们实际上通常是：

> 同一个模型，使用七套不同 Prompt、输入范围和 JSON Schema，扮演七种角色。

因此它更准确地说是“受限角色化模型调用”，而不是会互相讨论、自由选择工具、自己规划任务的多 Agent 系统。

所有 Agent 输出都必须通过严格 Pydantic Schema，额外字段会触发你之前看到的 `Extra inputs are not permitted`。Schema 定义在 [agent_schemas.py](../backend/idea/agent_schemas.py#L1)。

结构不合格、英文输出、证据 ID 不合法时，会要求模型在当前调用内修正。模型接口使用 OpenAI 兼容的 `/chat/completions`，实现位于 [model_client.py](../backend/idea/model_client.py#L138)。

## 八、用了哪些技术

主要技术没有特别花哨，重点是组合方式：

- Python：整个后端和 Workflow。
- FastAPI + Uvicorn：HTTP API 和服务运行。
- Pydantic：输入校验、Agent JSON Schema、禁止额外字段。
- asyncio：双 Provider 检索、全文抓取、逐篇文献分析、多 D1 路线并发。
- httpx：调用模型、Google Patents 和 MCP。
- MCP JSON-RPC：调用 EXA 工具。
- SQLite：保存 Case、Run、步骤、检索结果、证据、矩阵、审计和报告索引。
- 本地文件：保存输入快照、`report.json`、`report.md` 和 Manifest。
- SHA-256：检查输入、证据、阶段结果和报告有没有被改动。
- FIFO 缓存：限制为约 1 GiB，只清理可重新抓取的数据。
- ContextVar：把每个 Run 的 Base URL、API Key 和 Model 隔离开。
- SSE：前端接收 Run 状态变化。
- 原生 HTML/CSS/JavaScript：前端没有 React/Vue 等框架。
- JSONL：保存逐 Run 调试事件。

各组件的组装入口在 [runtime.py](../backend/idea/runtime.py#L35)。

## 九、当前设计做得比较好的地方

1. 模型没有控制 Workflow，降低了乱跳步骤和伪造执行的风险。
2. 新颖性采用单篇文献原则，由程序计算。
3. 每个披露判断尽量绑定真实原文证据。
4. 输入、阶段结果和报告有哈希，可以检查是否被修改。
5. 每个 Run 不覆盖历史，适合比较不同版本的技术方案。
6. 单个检索 Provider 失败时可以降级运行。
7. API Key 不写入数据库、报告、浏览器存储和调试日志。
8. 把“模型主观意见”和“程序能证明的事实”分开了。
9. 审计 Agent 即使声称发现了 critical，也不能凭主观判断直接让系统失控；真正的硬阻断主要来自日期、哈希、证据归属等程序校验。

## 十、目前主要不足

### 1. 最弱的一环仍然是检索召回率

Google Patents 是网页抓取，不是稳定的官方结构化 API。网页结构变化、限流、网络代理和反爬都会影响结果。

摘要初筛主要依赖词项覆盖，没有向量语义检索、专业专利分类扩展或成熟重排模型。复杂同义表达可能被漏掉。

所以系统能证明的是：

> “在本次实际检索到并深读的文献范围内，结论是什么。”

它不能证明：

> “全世界一定不存在更早的相关文献。”

### 2. 法律规则被简化了

当前主要根据专利公开日和评估日过滤。正式现有技术判断还可能涉及：

- 优先权日；
- 申请日；
- 首次公开时间；
- 抵触申请；
- 不同法域的特殊规则；
- 非专利文献公开；
- 公开是否充分；
- 权利要求解释。

这些目前没有形成完整的法域规则引擎。因此它是技术预评估，不是正式法律意见。

### 3. Agent 之间并不真正独立

Parser、文献分析、创造性、价值、审计和报告可能都由同一个模型执行。

虽然角色和上下文隔离了，但同一个模型的偏见可能贯穿全部环节。设计文档提到“高风险文献由第二个独立实例复核”，但当前文献分析代码里还没有真正看到双模型或独立复核实现。

### 4. 价值评分没有外部商业数据

价值 Agent 没有接入：

- 市场规模；
- 竞品销量；
- 专利交易；
- 诉讼；
- 标准必要性；
- 申请人和竞争对手布局。

所以“技术/市场价值 4/5”只是基于 IDEA 和专利分析结果的初步判断，不是商业尽调评分。

### 5. 运行成本和稳定性仍受模型影响

一次 Run 可能包括：

- 1 次 IDEA 解析；
- 1 次检索规划；
- 10～40 次逐篇分析；
- 最多 3 次创造性分析；
- 价值、审计、报告各一次；
- 失败时还有重试。

因此运行时间、Token 成本和失败概率都会随着深读数量增加。Schema 和证据门禁能阻止错误结果落库，但不能消除模型偶发空响应、格式错误或判断波动。

### 6. 还不是生产级多用户系统

当前使用单机 SQLite、本地目录和进程内 `asyncio.Task`：

- 没有任务队列；
- 没有多机器调度；
- 没有用户账号；
- 没有权限隔离；
- 所有人可以看到共享 Case；
- API 层没有真正的身份认证；
- SQLite 不适合大量并发写入和横向扩容。

适合内部单机或小团队使用，不适合直接部署成开放式 SaaS。

### 7. 服务重启不能继续原 Run

这是安全设计和可恢复性之间的取舍。

因为 API Key 坚持不落盘，所以服务重启以后，正在运行的任务会因为失去临时 Token 而失败。步骤和历史不会丢，但必须重新输入 API 配置并创建一个新 Run。

### 8. 入口仍残留旧系统代码

虽然当前页面只展示 IDEA，但 [main.py](../backend/main.py#L117) 仍保留旧文件管理、上传和 `/api/run` OpenCode 任务接口。

这会带来两个问题：

- 新旧架构边界不够干净；
- 增加不必要的 API 和安全维护面。

后续最好把旧接口归档、加开关，或者拆成独立服务。

### 9. 自动测试多，但专业评测还不够

目前单元测试、契约测试和 Workflow 测试不少，也做过真实端到端 Run。但还没有看到持续运行的专业 Eval 数据，例如：

- 已知专利集的检索召回率；
- 特征映射准确率；
- 新颖性结论一致率；
- 不同模型之间的稳定性；
- 虚假证据率；
- 与专业检索员结果的对照；
- 单次成本和耗时分布。

代码“能跑通”和“专利判断长期可靠”是两件不同的事。现在第一件已经做得不错，第二件仍需系统评测。

## 总体评价

如果按阶段来评价：

- 作为 Prompt Demo：已经远远超过。
- 作为内部专利评估 MVP：架构合理，证据和审计设计较强。
- 作为稳定的团队内部工具：基本可用，但需要继续提升检索质量和运行稳定性。
- 作为正式法律分析系统：还不够。
- 作为多用户生产 SaaS：基础设施、权限和安全边界还没到位。

我认为当前最有价值的设计是“模型负责语义，程序负责事实和控制”；最需要继续投入的三个方向依次是：

1. 建立可量化的专利检索与判断 Eval；
2. 提升检索召回、同族识别和法域日期规则；
3. 引入真正独立的高风险复核模型或人工复核节点。

# AI4Patent IDEA 下一阶段架构与开发建议

> - 文档类型：架构评审与下一阶段实施路线图
> - 评审日期：2026-07-16
> - 评审对象：`backend/idea`、IDEA Web 工作台及其运行基础设施
> - 当前基线：固定 11 步 Workflow、双 Provider 检索、证据矩阵、逐 Run 持久化、运行时 BYOK
> - 文档用途：供产品负责人、架构师和后续开发 Agent 共同确定下一阶段范围；不是已经完成的功能清单

## 1. 执行摘要

当前 IDEA 模块已经完成了从“单次 Prompt Demo”到“可审计 Workflow MVP”的关键跨越。系统最有价值的资产不是某一条 Prompt，而是以下工程边界：

- 后端状态机控制执行顺序，模型不能自行跳步；
- 检索、日期、去重、证据归属、哈希和完成门禁由确定性程序负责；
- 模型只处理语义任务，并通过严格 JSON Schema 输出；
- 每个 Run 是不可覆盖的输入、过程和报告快照；
- 新颖性遵守单篇文献原则，证据可以回指原文；
- API Key 仅在当前 Run 的进程内存中存在。

下一阶段不应继续以“增加更多 Agent”作为主线，而应把系统从“能完成一次分析”提升到“能够证明分析质量、稳定控制成本、明确法律边界并安全地供团队长期使用”。

建议下一阶段的产品定位是：

> 面向内部研发、IP 团队和专利代理师的专利检索与申请前决策支持系统；输出是带证据和限制的预评估，不是自动出具法律意见。

建议未来 8～12 周集中完成四项核心能力：

1. 建立固定 Eval 数据集和质量基线，让检索召回率、映射准确率和结论稳定性变得可测；
2. 重构检索排序与同族处理，提高真正相关文献进入深读队列的概率；
3. 建立法域化的现有技术日期策略和高风险双重复核机制；
4. 收敛旧接口、权限、任务执行和数据保留边界，使系统达到可靠的内部生产级。

## 2. 当前架构判断

### 2.1 当前系统属于哪一种 Agent 架构

当前实现不是“自主多 Agent 系统”，而是“确定性 Harness 管理的角色化模型调用”。七种 Agent 角色通常共享同一个底层模型，只是 Prompt、输入范围和输出 Schema 不同。

这是一项正确选择。专利分析需要可重放、可审计和可失败关闭，不适合让主 Agent 自由规划或自主选择是否跳过检索。下一阶段应继续坚持：

```text
Workflow 决定做什么
Deterministic Service 决定哪些事实成立
Agent 解释受限上下文中的语义
Validator 决定模型输出能否被接受
Audit 决定 Run 能否进入成功终态
```

### 2.2 当前主要优势

| 能力 | 当前评价 | 保留建议 |
|---|---|---|
| 固定 Workflow | 强 | 保持固定有向流程，不改成自由 Agent 编排 |
| Run 不可覆盖 | 强 | 继续作为全部恢复、审计和比较的基础 |
| 证据 ID 与哈希 | 强 | 扩展到 Claim、日期来源和 Provider 原始记录 |
| 单篇新颖性原则 | 强 | 保持确定性裁决，不交给报告 Agent |
| 双 Provider 降级 | 中上 | 增加 Provider 能力矩阵和质量统计 |
| 结构化输出门禁 | 中上 | 增加 Prompt/Schema 版本和模型兼容性记录 |
| 创造性路线 | 中 | 证据边界合理，但 D1/D2 选择仍较简化 |
| 价值评分 | 中下 | 适合作为预评估，不足以支持商业价值结论 |
| 可观测性 | 中上 | 事件齐全，但缺少聚合指标、费用预算和告警 |
| 部署与权限 | 弱 | 目前只适合可信内网和少量并发 |

### 2.3 核心问题不是“模型还不够聪明”

当前最主要的质量上限来自检索和证据入口，而不是报告写作。即使换用更强模型，如果候选召回不足、同族去重不准、评估日规则不完整或证据片段没有覆盖关键 Claim，最终结论仍然会偏差。

因此后续投入顺序应当是：

```text
质量评测基线
→ 检索召回与排序
→ 现有技术日期与证据质量
→ 高风险复核
→ 运行平台和权限
→ 报告与交互体验
```

## 3. 下一阶段目标架构

建议目标架构保持模块化单体，不立即拆微服务：

```text

                              │ HTTP + SSE
┌─────────────────────────────▼────────────────────────────────┐
│ Application Layer                                            │

└─────────────────────────────┬────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────┐
│ Workflow Harness                                             │
│ 固定状态机、检查点、重试策略、预算、取消、完成门禁            │
└───────────────┬───────────────────────────┬──────────────────┘
                │                           │
┌───────────────▼──────────────┐  ┌─────────▼─────────────────┐

│ 日期策略、同族、排序、矩阵、 │  │ Parser/Planner/Analyzer/  │
│ 证据验证、审计、报告事实装配 │  │ Inventive/Value/Audit/    │
│                              │  │ Report/Independent Review │
```

近期继续使用单体的原因：

- 当前复杂度主要在业务正确性，不在服务吞吐；
- 模块边界已经通过 Python Service 和 Provider Contract 建立；
- 过早拆服务会放大事务、恢复、密钥传递和本地开发成本；
- 等出现多 Worker、远程队列或多租户的真实需求后，再拆任务执行层。

## 4. 架构原则与强制边界

后续开发建议遵守以下原则。

### 4.1 权威事实只能来自确定性来源

- 公开号、申请号、日期、申请人、同族、章节位置来自 Provider 原始结果和程序解析；
- Agent 只允许解释，不允许修正或猜测这些字段；
- 日期缺失或来源冲突必须保留多个值和来源，不能静默选择；
- 报告中的统计数字由后端注入，禁止 Agent 自行计算。

### 4.2 结论必须与证据强度匹配

- `NOT_NOVEL` 必须有单篇完整覆盖；
- `NOVEL` 必须同时满足深读下限、停止条件和逐篇明确缺口；
- 创造性 `NOT_INVENTIVE` 必须有逐区别特征 D2 证据和组合动机依据；
- 证据不足时降级为 `UNCERTAIN/NEED_MORE_EVIDENCE`，不能用流畅叙述掩盖缺口；
- 价值判断必须显式区分“技术推断”和“外部市场事实”。

### 4.3 Agent 不直接拥有外部工具权限

下一阶段即使增加 Provider，也应由 Retrieval Service 调用。Agent 只能提交结构化的检索计划或“需要补证据”的请求，由 Workflow 判断是否允许进入新增的补充检索步骤。

### 4.4 每一项质量改进必须可评测

不得只以“报告看起来更好”作为验收。每次检索、排序、Prompt、模型或证据包调整都必须在固定 Eval 集上产生可比较的指标。

### 4.5 历史不可变与隐私治理必须同时成立

Run 历史不可自动覆盖，但这不等于数据必须永久保存。应增加明确的保留策略、导出和受控删除能力，并在未来启用用户体系后限定谁能查看和删除。

## 5. 优先级风险清单

### P0：没有固定 Eval，无法判断系统是否真的变好

现有测试主要证明代码契约、状态机和故障语义正确，尚不能证明专利检索与判断的业务准确率。

风险：

- 修改排序后可能让测试全通过，但召回率下降；
- 更换模型后报告更流畅，但特征映射一致率下降；
- Prompt 修复一个案例时可能破坏其他技术领域；
- 无法给用户说明“系统在什么范围内可信”。

处置：下一阶段第一个工作单元必须是 Eval 基线，先测量，再优化。

### P0：检索和排序仍是质量瓶颈

当前摘要初筛以中英文词项覆盖为主，对复杂同义表达、功能性特征、跨领域术语和 Claim 相关但摘要不相关的专利召回不足。

风险：真正关键文献没有进入深读队列，后面的证据审计再严格也无法发现它。

处置：建立混合排序、分类号扩展、候选多样性控制和检索覆盖报告。

### P0：法律日期模型过于单一

当前主要按公开日与评估日比较。真实现有技术判断可能涉及优先权、申请、公开、抵触申请和法域规则。

风险：系统将“技术上相关”错误表达为“法律上可用的现有技术”。

处置：增加 `PriorArtPolicy` 和日期资格状态，不再把单个日期比较散落在检索、新颖性和审计代码中。

### P0：内部系统边界尚未收敛

当前主服务仍保留旧 `/api/run`、文件上传和删除接口，且没有用户身份与权限模型。

风险：

- 新旧执行路径混淆；
- 多余接口扩大攻击和维护面；
- 任意内部访问者可以查看或删除共享历史；
- 用户技术方案和专利证据长期明文保存在本机。

处置：先通过功能开关关闭旧入口，再建立最小身份、角色和审计策略。

### P1：所谓独立审计并不真正独立

七种 Agent 可由同一个底层模型执行。审计 Agent 能检查遗漏和表述，但可能继承前序 Agent 的相同偏差。技术设计中的“高风险文献第二实例复核”尚未形成完整实现。

处置：定义高风险触发条件、盲审输入、第二模型配置和冲突裁决流程。

### P1：单机异步任务不适合生产并发

当前任务保存在进程内，SQLite 承担全部写入。服务重启后因 API Key 不落盘而无法恢复原 Run，这是合理的安全边界，但多 Worker 部署会产生任务归属和运行时配置路由问题。

处置：近期维持单进程 Worker；只有在并发和部署目标明确后，再引入数据库租约或任务队列。

### P1：成本、延迟和限流缺少统一预算

一次深度 Run 可能产生几十次模型调用和网络请求。当前有并发数、超时和重试，但缺少 Run 级最大 Token、最大费用、最大 Provider 调用和熔断策略。

处置：新增 `RunBudget`、调用前预算检查、Provider 熔断和报告成本摘要。

### P2：前端适合 MVP，但不适合复杂人工复核

当前前端可以查看结果和日志，但对 Claim—特征—证据的关系展示不足，也没有人工确认、驳回、批注和 Run 差异比较。

处置：等 Eval、日期和证据模型稳定后，再建设人工复核工作台。

## 6. 工作流级改造建议

不建议立即把 11 步完全推翻。建议保留主流程，同时增加两个可选门禁和一个补充检索循环：

```text
PREPARE_INPUT
PARSE_IDEA
VALIDATE_IDEA_MODEL
PLAN_QUERIES
RETRIEVE_CANDIDATES
NORMALIZE_AND_FETCH
ANALYZE_DOCUMENTS
DETERMINE_NOVELTY
ASSESS_EVIDENCE_GAPS       # 新增：程序判断是否需要补充检索
SUPPLEMENTAL_RETRIEVAL     # 可选：最多 N 轮，受预算和停止条件控制
ANALYZE_INVENTIVENESS
ASSESS_VALUE
INDEPENDENT_REVIEW         # 可选：高风险 Run 才触发
AUDIT_AND_REPORT
```

### 6.1 补充检索不得由 Agent 自主循环

`ASSESS_EVIDENCE_GAPS` 应由程序根据以下信号决定是否补检索：

- 关键特征在全部文献中均为 `UNCERTAIN`；
- 创造性路线缺少某个区别特征的 D2；
- 检索尚未饱和但因计划检索式耗尽停止；
- 高相关候选数量低于深读下限；
- Provider 只有一路成功；
- IPC/CPC 覆盖范围明显不足。

补充检索请求可以让 Query Planner 生成 `distinguishing_feature` 类型的新检索式，但必须满足：

- 最大补充轮数；
- 最大新增 Provider 调用数；
- 最大候选数；
- 每轮明确记录触发原因；
- 不得重复执行相同规范化查询；
- 达到预算后必须停止并写入限制。

### 6.2 每一步增加显式重试策略

当前主要使用统一 attempt 上限。建议为不同错误建立分类策略：

| 错误类型 | 推荐行为 |
|---|---|
| 模型 JSON/中文门禁失败 | 同一 Agent 调用内结构化重试 |
| 模型 429/5xx/超时 | 指数退避，遵守 Run 预算 |
| Provider 单路失败 | 记录降级，继续其他 Provider |
| 全部 Provider 暂时失败 | Workflow step 重试 |
| 证据哈希/跨文献引用错误 | fail closed，不做无意义网络重试 |
| 日期规则冲突 | 转人工复核或 `UNCERTAIN` |
| 报告叙述冲突 | 只重试 Report Composer，不重跑前序分析 |

### 6.3 明确幂等和恢复契约

每个步骤应记录：

- `step_contract_version`；
- `input_fingerprint`；
- `output_schema_version`；
- `prompt_version`；
- `model_provider/model_name`；
- `retry_classification`；
- `reusable_after_restart`。

如果输入指纹、代码契约和结果哈希一致，恢复时优先复用检查点。Prompt 或 Schema 版本变化时，不应在原 Run 上静默复算，应创建新的 Run 或明确的迁移 Run。

## 7. 检索系统改造

### 7.1 建立 Provider 能力矩阵

每个 Provider 不应只有 `search/fetch` 两个抽象方法，还应声明能力：

- 是否支持公开号精确检索；
- 是否支持 IPC/CPC；
- 是否返回优先权、申请、公开和授权日期；
- 是否返回同族 ID；
- 是否提供结构化 Claims；
- 支持语言；
- 分页能力；
- 最大结果数和速率限制；
- 数据来源和服务条款风险。

Workflow 根据能力选择 Provider，报告显示实际使用了哪些能力，而不是只显示 Provider 名称。

### 7.2 将排序拆成可解释的多阶段漏斗

建议候选排序改为：

```text
阶段 A：硬过滤
公开号有效、日期资格、重复项、URL 可追踪

阶段 B：词项与分类召回
中文/英文术语、同义词、IPC/CPC、功能描述

阶段 C：轻量语义重排
标题、摘要、独立 Claim 摘要与 F1..Fn 的语义相关度

阶段 D：多样性选择
避免前 N 篇全部来自同族、同一申请人或同一检索式

阶段 E：全文深读
权利要求优先，再选择说明书相关片段
```

第一阶段不必马上引入向量数据库。可以先使用可插拔 `Reranker` 接口，在候选数量较小时在线计算语义分数，并把每个分数组成部分持久化。只有文档规模和复用需求证明必要后，再引入本地向量索引。

### 7.3 改进同族与重复项处理

当前标题、优先权日和申请人只产生可能同族提示，这是保守且正确的。下一步建议：

- 分离“确定同族”和“疑似同族”；
- 保存同族关系来源和置信级别；
- 深读预算默认按独立披露计数，而不是简单按公开号计数；
- 同族中优先选择 Claim 和日期信息最完整的代表文献；
- 不确定同族不得静默合并；
- 报告同时展示公开号数量和独立披露数量。

### 7.4 增加检索覆盖说明

每个 Run 应生成结构化 `search_coverage`：

- 使用的中英文概念组；
- 使用和未使用的 IPC/CPC；
- 每个检索式的新增独立披露数；
- 每个 Provider 的成功率和重复率；
- 停止原因；
- 未覆盖的特征或术语；
- 因预算、限流、日期缺失而排除的候选数量。

这比单纯显示“检索了 80 篇”更能解释结论可信度。

## 8. 法律日期与现有技术资格模型

建议新增独立领域服务：

```python
class PriorArtPolicy(Protocol):
    def assess(document, evaluation_context) -> PriorArtEligibility: ...
```

`PriorArtEligibility` 至少包含：

- `status`: `ELIGIBLE / INELIGIBLE / POTENTIAL_CONFLICTING_APPLICATION / UNKNOWN`；
- `jurisdiction`；
- `relevant_date`；
- `date_type`；
- `source_provider`；
- `rule_code`；
- `rationale`；
- `limitations`。

建议分两步实施：

1. 第一版只明确支持“公开日在评估日前”的公开现有技术，并把其他情况标为 `UNKNOWN`，不再使用模糊的默认资格；
2. 第二版按目标法域增加优先权、抵触申请和特殊日期规则，并要求专业人员确认规则文本。

前端需要把“评估日”与“目标法域”分开。评估日是截止日期，目标法域决定日期的法律使用方式。日期依据继续只用于说明用户为什么选择该日期。

## 9. Agent 可靠性改造

### 9.1 建立 Agent Registry

当前 Agent 名称、Prompt 和 Schema 分散在多个模块。建议建立只读 Registry，记录：

- Agent 名称；
- Prompt 版本；
- 输入 Schema 版本；
- 输出 Schema 版本；
- 允许读取的数据类型；
- 禁止行为；
- 支持的模型能力；
- 最大输入字符和输出 Token；
- 失败分类与重试策略。

Run 报告和 Tool Call 必须保存这些版本信息，便于比较模型或 Prompt 升级前后的结果。

### 9.2 实现真正的高风险独立复核

建议高风险触发条件：

- 结论为 `NOT_NOVEL`；
- 新颖性为 `NOVEL` 且计划用于申请决策；
- 文献映射置信度接近阈值；
- Claim 与摘要结论冲突；
- 创造性为 `NOT_INVENTIVE`；
- Auditor 报告语义过度；
- Provider 日期或公开号存在冲突。

复核原则：

- 第二实例只获得相同的冻结证据，不读取第一实例理由，避免锚定；
- 优先使用不同模型或不同 Provider；如果只能使用同一模型，至少记录“不具备模型独立性”；
- 第二实例不能直接覆盖第一结果；
- 程序比较特征状态、证据引用和结论；
- 一致则提高“复核状态”，不直接提高统计置信度；
- 不一致则进入 `REVIEW_REQUIRED` 或降级为 `UNCERTAIN`；
- 所有冲突保留在报告中，由人工裁决。

### 9.3 不建议引入自由对话式 Agent 协商

多个 Agent 互相辩论可能改善个别文本，但会降低可重放性、增加 Token 成本，并让证据来源变得模糊。应优先使用“独立盲审 + 程序比较 + 人工裁决”。

### 9.4 允许模型能力差异，但不能降低契约

运行时 BYOK 允许用户输入不同兼容模型。建议增加模型能力探测：

- 是否支持 `response_format=json_object`；
- 上下文长度；
- 最大输出；
- 是否稳定返回 usage；
- 是否允许并发；
- 结构化输出历史成功率。

如果模型不支持某能力，应选择兼容请求方式或在 Run 开始前失败，不应在运行中途才发现。

## 10. 证据与文献分析改造

### 10.1 Evidence Packet 从词项相关升级为分层证据

建议证据包固定分层：

1. 独立权利要求全文或受控分段；
2. 摘要；
3. 与每个必要特征对应的说明书片段；
4. 术语定义和附图说明；
5. 日期和同族来源记录。

每个片段记录 `selection_reason`，例如：

- `INDEPENDENT_CLAIM`；
- `LEXICAL_MATCH:F3`；
- `SEMANTIC_MATCH:F2`；
- `DEFINITION`；
- `DATE_SOURCE`。

### 10.2 增加 Claim 级结构

当前证据可以引用 Claim 文本，但缺少稳定的 Claim 层级关系。建议增加：

- Claim 编号；
- 独立/从属类型；
- 父 Claim；
- Claim 文本哈希；
- Provider 解析置信度；
- 特征映射所在 Claim；
- 是否仅由说明书支持而未进入 Claim。

这能显著改善创造性分析和后续申请策略建议。

### 10.3 不要过早删除难以重建的原文

当前成功分析后会释放业务库中的可重建全文，依赖缓存重新获取。建议区分：

- 可稳定重新抓取的公开文献正文；
- Provider 条款允许缓存但可能变化的正文；
- 用户上传且不可重新获取的材料；
- 已进入最终结论的关键证据上下文。

至少应长期保留关键证据片段、Claim 哈希、原始来源 URL、抓取时间和解析器版本。对于不可重建材料，必须进入 Run Store，不得按普通缓存清理。

## 11. 价值分析边界

短期应把模块名称和报告表述稳定为“申请价值预评估”，避免让用户理解成完整专利估值。

建议将价值拆为两层：

### 第一层：当前可实现的专利工程评分

- 可取证性；
- 规避难度；
- 权利要求可概括空间；
- 与现有技术距离；
- 证据完整度；
- 申请文本准备度。

这些维度可主要依据 IDEA 和专利证据。

### 第二层：需要外部数据的商业价值

- 市场规模；
- 竞品和申请人布局；
- 标准必要性；
- 许可和诉讼；
- 产品收入关联；
- 剩余保护期限。

没有接入可信数据源时，第二层必须显示“未评估”，不能用模型常识打分代替事实。

## 12. 数据模型建议

建议在不破坏现有表的前提下逐步增加：

| 表/实体 | 用途 |
|---|---|
| `agent_definitions` | Prompt、Schema、权限和版本登记 |
| `run_budgets` | Token、费用、Provider 调用和时间预算 |
| `provider_capabilities` | Provider 能力快照 |
| `document_date_facts` | 多种日期、来源和冲突记录 |
| `prior_art_eligibility` | 按法域计算的现有技术资格 |
| `patent_claims` | Claim 层级、文本和哈希 |
| `ranking_features` | 候选排序各分项和排序版本 |
| `review_tasks` | 人工/独立模型复核任务 |
| `review_decisions` | 冲突、决定、操作者和理由 |
| `eval_cases` | 固定评测样本元数据 |
| `eval_runs` | 代码/Prompt/模型版本下的评测结果 |
| `run_metrics` | Token、费用、延迟、调用数和质量摘要 |

数据迁移原则：

- 只追加迁移，不原地改写历史报告；
- 新字段缺失时明确显示旧版本语义；
- 每个派生结果保存生成规则版本；
- Eval 数据与真实用户数据物理或逻辑隔离；
- API Key 永远不进入上述任何表。

## 13. API 与前端建议

### 13.1 收敛旧 API

建议新增 `features.legacy_runtime_api` 配置，默认关闭：

- `/api/run`；
- `/api/stop`；
- 通用 `/api/files`；
- 与当前 IDEA 无关的上传/下载接口。

之后将旧 OpenCode 执行入口迁出 `main.py` 或放入独立 Router。IDEA 上传应使用 Run 作用域接口，避免全局文件目录。

### 13.2 增加复核 API

建议后续增加：

```text
GET  /api/idea/runs/{run_id}/evidence
GET  /api/idea/runs/{run_id}/claims
GET  /api/idea/runs/{run_id}/coverage
GET  /api/idea/runs/{run_id}/metrics
POST /api/idea/runs/{run_id}/reviews
POST /api/idea/reviews/{review_id}/decision
GET  /api/idea/runs/{left}/compare/{right}
```

### 13.3 前端优先做证据浏览，不优先做视觉重构

建议新增三个高价值界面：

1. 特征—文献矩阵：点击单元格直接查看原文证据；
2. 检索覆盖：查看每条查询带来的新增文献、重复项和停止原因；
3. Run 比较：比较输入、F 特征、检索范围、结论和限制变化。

UI 美化应放在证据和复核能力之后。

## 14. 安全、隐私与权限

### 14.1 近期最低安全基线

- 默认仅监听 `127.0.0.1`；
- 如果监听非本机地址，必须启用身份认证；
- 关闭旧通用任务和文件接口；
- 所有删除操作记录操作者、对象和时间；
- 下载报告和证据需要与查看权限一致；
- API Key、Authorization、完整模型请求禁止写日志；
- 运行日志中的错误信息继续做敏感字段过滤；
- 增加数据库和 Run Store 的备份/恢复说明。

### 14.2 后续最小角色模型

建议三个角色足够：

- `viewer`：查看 Case、Run 和报告；
- `analyst`：创建 Run、提交复核和导出；
- `admin`：删除、配置 Provider、管理保留策略。

不要一开始设计复杂 RBAC，但必须避免所有访问者都能删除共享历史。

### 14.3 数据保留与加密

建议配置：

- 默认保留期限；
- 标记为长期保留的 Case；
- 手动导出后安全删除；
- 备份保留期；
- 本地磁盘加密要求；
- 用户上传材料与公开专利缓存分开存储。

Run 不可变是审计语义，不应阻止获得授权的删除请求。

## 15. 可观测性、SLO 与成本控制

### 15.1 Run 级指标

至少聚合：

- 总耗时、每步耗时和排队时间；
- 模型调用数、重试数、输入/输出 Token；
- Provider 请求数、成功率、超时率和结果数；
- 原始候选、去重候选、独立同族、深读成功数；
- Evidence 数量和平均每特征证据数；
- 结构化输出失败率；
- 复核冲突率；
- 最终状态和限制数量；
- 可选的估算费用。

### 15.2 建议内部 SLO

第一阶段先用观测值建立基线，不立即承诺过高目标。可以从以下内部目标开始：

- 离线测试通过率：100%；
- Workflow 非外部故障完成率：≥ 99%；
- 结构化输出单调用最终成功率：≥ 98%；
- Tool Call 和步骤日志完整率：100%；
- 引用未知 evidence ID 落库率：0；
- API Key 持久化和日志泄漏事件：0；
- 同一 Eval 输入结论稳定率：建立基线后设阈值；
- Quick 模式 P50/P95 完成时间：先测量再承诺。

### 15.3 RunBudget

建议 Run 创建时冻结：

- 最大模型调用数；
- 最大输入/输出 Token；
- 最大 Provider 调用数；
- 最大补充检索轮数；
- 最大墙钟时间；
- 可选最大估算费用。

达到预算时进入 `COMPLETED_WITH_LIMITATIONS` 或 `FAILED`，由当前证据是否足以生成有效报告决定。

## 16. Eval 与测试体系

### 16.1 固定 Eval 数据集

建议第一版至少 30 个案例，覆盖：

- 10 个明确存在单篇破坏新颖性的案例；
- 5 个需要 D1+D2 的创造性案例；
- 5 个后公开或日期陷阱案例；
- 5 个同族密集案例；
- 5 个跨领域、同义词或摘要弱相关案例。

每个案例应包含：

- 冻结的 IDEA 输入；
- 评估上下文和目标法域；
- 专家标注的必要特征；
- 必须召回的关键文献；
- 关键 Claim/段落；
- 允许的结论范围；
- 标注者和复核状态。

涉及真实客户方案时不能直接进入仓库。仓库内只保存可公开或合成的数据，私有 Eval 放在受控目录。

### 16.2 核心指标

检索：

- 关键文献 Recall@30、Recall@80；
- 深读队列 Recall@10、Recall@20；
- 高相关 Precision；
- 同族去重准确率；
- 后公开文献排除准确率。

文献分析：

- 必要特征识别一致率；
- `DISCLOSED/PARTIAL/NOT_DISCLOSED` 准确率；
- 证据章节正确率；
- 证据可定位率；
- 虚假证据率。

结论：

- 新颖性结论准确率；
- 创造性路线与专家意见一致率；
- 过度肯定率；
- 不同重复 Run 的结论稳定率；
- 限制披露完整率。

工程：

- 完成率；
- 重试率；
- P50/P95 时延；
- Token 和估算费用；
- Provider 故障恢复率。

### 16.3 测试分层

```text
大量：纯函数、Schema、日期、去重、状态机单元测试
中量：Provider fixture、数据库和 Workflow 集成测试
少量：固定模型响应的 Agent 契约测试
定期：真实 Provider 在线 smoke
受控：固定 Eval 集的真实模型回归
人工：高风险案例专家复核
```

真实模型 Eval 不应阻塞每个普通提交，但应在 Prompt、模型、排序或证据策略变更时运行，并保存结果对比。

## 17. 分阶段实施路线图

### 阶段 A：质量基线与边界收敛（建议 1～2 周）

目标：在继续增加功能前，先建立可测量和可安全运行的基线。

任务：

1. 新建 Eval 数据格式、CLI 和首批公开/合成样例；
2. 记录 Agent/Prompt/Schema/排序版本；
3. 新增 Run Metrics 和预算快照；
4. 用功能开关默认关闭旧 `/api/run` 和通用文件接口；
5. 增加服务监听与无认证状态健康警告；
6. 为当前 11 步生成一次基准报告。

验收：

- 同一提交可以重复运行固定 Eval；
- 输出机器可读指标和与上一基线的差异；
- 默认 IDEA 启动不暴露旧任务接口；
- 现有历史、报告和 BYOK 行为不回归。

### 阶段 B：检索、排序和同族质量（建议 2～4 周）

目标：提高关键文献进入深读队列的概率。

任务：

1. Provider 能力矩阵；
2. 排序特征持久化；
3. IPC/CPC 查询扩展；
4. 可插拔轻量语义 Reranker；
5. 同族代表文献策略和独立披露计数；
6. 检索覆盖报告；
7. 受预算控制的补充检索步骤。

验收：

- Eval 关键文献 Recall 不低于当前基线；
- Recall 提升同时不能显著恶化深读 Precision 和费用；
- 每篇入选文献能解释为什么进入深读；
- 补充检索有确定停止原因且不会无限循环。

### 阶段 C：日期策略、Claim 和独立复核（建议 2～3 周）

目标：提高法律边界表达和高风险结论可靠性。

任务：

1. `PriorArtPolicy` 与日期事实表；
2. 目标法域输入；
3. Claim 层级持久化；
4. 高风险触发器；
5. 独立盲审与冲突记录；
6. 人工复核 API 和最小 UI。

验收：

- 日期未知或规则不支持时不会被错误标成确定可用；
- `NOT_NOVEL/NOT_INVENTIVE` 高风险结论具有复核状态；
- 两次分析不一致时不会静默覆盖；
- 报告区分程序事实、模型判断和人工决定。

### 阶段 D：内部生产化（建议 2～4 周，按部署需求启动）

目标：支持可信团队长期使用，而不是立即建设公共 SaaS。

任务：

1. 最小认证和三角色权限；
2. 数据保留、备份和恢复；
3. 聚合 Metrics 和告警；
4. Run 级限额和 Provider 熔断；
5. Run 比较和证据浏览；
6. 并发压力测试；
7. 决定是否从 SQLite 迁移 PostgreSQL、是否引入 Worker 队列。

触发 PostgreSQL/队列迁移的条件建议为：

- 需要多个服务进程同时执行 Run；
- SQLite 写锁成为可观测瓶颈；
- 需要远程 Worker；
- 需要任务租约、重分配或横向扩容；
- 单机故障恢复目标无法满足。

在这些条件出现前，不建议为“架构看起来先进”而提前迁移。

## 18. 第一轮开发任务建议

下一次实际开发建议只做一个可闭环的工作包：`IDEA-EVAL-001`。

### 18.1 范围

- 定义 Eval Case JSON Schema；
- 建立 5～10 个不含私密信息的初始案例；
- 实现离线评分器，先支持已冻结检索结果和 Agent 输出；
- 计算特征一致率、证据可定位率、新颖性结论一致率和工程指标；
- 输出 `eval-summary.json` 和 `eval-summary.md`；
- 保存代码版本、Prompt/Schema 版本、模型和配置摘要；
- 增加回归测试；
- 在开发日志中追加基线结果。

### 18.2 不包含

- 不立刻加入向量数据库；
- 不重写现有 Workflow；
- 不同时加入用户系统；
- 不在同一提交里更换检索排序算法；
- 不把真实用户历史复制到 Git。

### 18.3 验收标准

- 评测输入和预期结果有 Schema；
- 同一 fixture 重复评分结果一致；
- 未知证据、跨文献证据和日期错误会被评分器识别；
- 能比较两个 Eval Run 并指出指标变化；
- 不记录 API Key、完整 Authorization 或私有用户数据；
- 全量现有测试继续通过；
- 文档明确哪些指标是自动评分，哪些需要专家标注。

## 19. 建议提交边界

后续继续使用小而可回滚的提交，建议主题如下：

```text
docs(idea): [IDEA-ADR-001] define quality and legal boundaries
feat(idea): [IDEA-EVAL-001] add reproducible evaluation harness
feat(idea): [IDEA-METRICS-001] persist run cost and quality metrics
refactor(api): [IDEA-BOUNDARY-001] gate legacy runtime endpoints
feat(idea): [IDEA-RETRIEVE-002] persist ranking signals and coverage
feat(idea): [IDEA-RERANK-001] add hybrid candidate reranking
feat(idea): [IDEA-FAMILY-001] count independent disclosures
feat(idea): [IDEA-DATE-001] introduce prior-art policy
feat(idea): [IDEA-CLAIM-001] persist claim-level evidence
feat(idea): [IDEA-REVIEW-001] add independent high-risk review
feat(idea): [IDEA-AUTH-001] add minimal internal access control
```

每个提交都应包含：

- 一项明确行为变化；
- 对应单元/集成测试；
- 必要的 Schema 和迁移；
- 追加式开发日志；
- 与固定 Eval 基线的对比（影响业务质量时）；
- 不包含 API Key、真实客户输入或运行缓存。

## 20. 明确暂缓的事项

当前不建议立即实施：

- 自由自主的多 Agent 群体协商；
- Kubernetes 和微服务拆分；
- 为少量候选直接部署大型向量数据库；
- 在没有专业标注前训练自有专利模型；
- 自动生成可直接提交的正式法律意见；
- 用模型主观置信度代替检索覆盖与证据指标；
- 一次性支持全部法域；
- 公网开放且无认证的多用户服务；
- 在同一个大提交中同时更换 Provider、Prompt、排序和数据模型。

## 21. 需要产品负责人确认的决策

在阶段 C/D 开始前，需要明确：

1. 第一目标法域是中国、PCT、美国还是仅做通用技术检索；
2. 系统是否只部署在单人本机，还是面向内部团队；
3. 用户方案和上传材料的默认保留期限；
4. 哪些结论必须进入人工复核；
5. 是否允许配置第二模型用于独立复核；
6. 单次 Run 可接受的时间和费用上限；
7. 是否计划接入商业专利数据源；
8. 价值模块是否只做申请工程评分，还是未来接入商业数据；
9. 哪一类报告可以对外发送，哪一类只能内部参考。

这些选择会改变数据模型、权限、日期规则和运行成本，不应由开发 Agent 自行假设。

## 22. 最终建议

下一阶段成功的判断标准不应是“又增加了几个 Agent”，而应是：

- 系统能够用固定 Eval 证明检索和判断没有退化；
- 每个结论都能说明检索范围、证据、日期资格和限制；
- 高风险结论有真正独立的复核或明确要求人工确认；
- Provider、模型和网络波动不会制造伪成功；
- 团队能够安全查看、比较、导出和删除自己的历史；
- 架构仍然保持简单，只有在真实规模要求出现时才引入队列、PostgreSQL或服务拆分。

推荐立即从 `IDEA-EVAL-001` 开始。它是后续检索、Agent、Prompt和模型改进的共同度量基础，也是当前从“工程上可运行”走向“业务上可证明”的最短路径。
